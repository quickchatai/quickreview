## A state-machine scan — state-machine defects and state-machine lenses only (state-machines profile; supersedes the defect list, the `kind:` word and the lenses your SUGGEST block names above)
This scan looks for defects of implicit state machines and nothing else: behaviour that depends on which state a thing is in, where the states and the moves between them are written down nowhere — spread over boolean flags, nullable fields, a status value, a stored column, a lifecycle phase or the order calls must come in.

- **Findings.** Report a defect only when a sequence of events reaches a state the code mishandles, and you can cite the state, the event and the line that acts with no check. A list of the state machines a file contains is not a finding, and neither is a combination the type can hold that nothing writes. A crash, a logic error or a style point with no state in it is left out, however real: no lens of this scan is asked to judge it. Every finding's `kind:` is `state-machine:<class>`, one of `illegal-state`, `transition`, `unhandled-state`, `stuck`, `event-order`, `derived`, `lifecycle`, `stored`, named the same way every time.
- **Suggestions.** Every SUGGEST row names a `pass-sm-*` lens from your task string's list, never another. The reason says what the lens should chase in state terms: the field that holds the state, how many places write it, the event source, the exit that looks unguarded. Where you would have pointed a quality, consistency or delivery lens, point the state-machine lens whose concern the code shows, or leave the file to the floor.
- **Where to point.** Types and models with several flags or with nullable fields beside a status get `pass-sm-states`; code that writes a status, state, phase or stage — above all from more than one place — gets `pass-sm-transitions`; enums, unions and status constants with dispatches, lists or maps over them get `pass-sm-exhaustive`; loading, processing, locked or in-progress markers and the code between their set and reset get `pass-sm-stuck`; webhook routes, queue consumers, timers, subscriptions and submit handlers get `pass-sm-events`; stored counts, totals, caches, mirrored flags and state set inside an effect get `pass-sm-derived`; objects with init, start, open, close, dispose or teardown get `pass-sm-lifecycle`; stored status columns, state writes beside an external call, durable workflows, sagas, migrations of a status and resume-after-restart code get `pass-sm-durable`.
