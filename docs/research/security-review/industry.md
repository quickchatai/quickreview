# How AI security reviewers and vulnerability hunters are designed

Researched 2026-11-02. Purpose: inform a security-focused review profile (split security lenses, lens reasoning, validator behaviour) for a **read-only** LLM reviewer that greps and reads a worktree but never executes code.

Source quality legend: **[repo]** = I read the actual prompt/code in the cloned repository at the cited commit; **[vendor]** = vendor's own blog/docs page fetched directly; **[snippet]** = the primary page refused my fetcher (HTTP 403) and the claim comes from search-result quotes of that page; **[secondary]** = press/third-party only. Vendor numbers are self-reported unless stated otherwise.

## 1. Anthropic

### 1.1 `claude-code-security-review` GitHub Action [repo, commit 0c6a49f, 2026-02-11]

**Pipeline.** One Claude Code audit pass over the PR → regex "hard exclusion" filter → one LLM call *per finding* to judge false positives → post comments. Source: https://github.com/anthropics/claude-code-security-review/blob/0c6a49f1fa56a1d472575da86a94dbc1edb78eda/claudecode/findings_filter.py

**Audit prompt scope.** "Identify HIGH-CONFIDENCE security vulnerabilities that could have real exploitation potential… focus ONLY on security implications newly added by this PR. Do not comment on existing security concerns." Source: https://github.com/anthropics/claude-code-security-review/blob/0c6a49f1fa56a1d472575da86a94dbc1edb78eda/claudecode/prompts.py

**Confidence instruction in the audit prompt.** "Only flag issues where you're >80% confident of actual exploitability"; scale: 0.9–1.0 "Certain exploit path identified, tested if possible", 0.8–0.9 "Clear vulnerability pattern with known exploitation methods", 0.7–0.8 "Suspicious pattern requiring specific conditions to exploit", "Below 0.7: Don't report (too speculative)". Closing line: "Better to miss some theoretical issues than flood the report with false positives." Source: same prompts.py.

**Categories (one generic prompt, five groups).** Input validation (SQLi, command injection, XXE, template injection, NoSQL injection, path traversal); AuthN/AuthZ (auth bypass, privilege escalation, session management, JWT, authorization logic bypass); Crypto & secrets (hardcoded keys, weak algorithms, key storage, randomness, certificate-validation bypass); Injection & code execution (deserialization RCE, pickle, YAML, eval, XSS); Data exposure (sensitive-data logging, PII handling, API endpoint data leakage, debug info). Plus "Even if something is only exploitable from the local network, it can still be a HIGH severity issue." Source: same prompts.py.

**Methodology given to the model.** Phase 1 "Repository Context Research" (existing security frameworks, sanitization patterns, the project's security model); Phase 2 "Comparative Analysis" ("Compare new code changes against existing security patterns… Flag code that introduces new attack surfaces"); Phase 3 "Vulnerability Assessment" ("Trace data flow from user inputs to sensitive operations… privilege boundaries being crossed unsafely"). Required fields per finding include `exploit_scenario` and `confidence`. Source: same prompts.py.

**Exclusions in the audit prompt.** DoS / resource exhaustion; secrets stored on disk; rate limiting; memory/CPU exhaustion; "Lack of input validation on non-security-critical fields. If there isn't a proven problem from a lack of input validation, don't report it." Source: same prompts.py.

**Stage 2a – deterministic hard-exclusion regexes** applied to finding title+description: DoS/resource exhaustion/unbounded recursion; missing rate limiting; resource/connection leaks; open redirect; regex injection/ReDoS; memory-safety terms *unless the file is .c/.cc/.cpp/.h*; SSRF *in .html files*; any finding in a `.md` file. Source: https://github.com/anthropics/claude-code-security-review/blob/0c6a49f1fa56a1d472575da86a94dbc1edb78eda/claudecode/findings_filter.py

**Stage 2b – per-finding LLM FP filter.** Each surviving finding is sent alone, with the full content of its file and the PR title/description, asking "determine if it's a false positive". Output: `confidence_score` 1–10 ("1-3: Low confidence, likely false positive or noise; 4-6: Medium confidence, needs investigation; 7-10: High confidence, likely true vulnerability"), `keep_finding` boolean, `exclusion_reason`, `justification`. Source: https://github.com/anthropics/claude-code-security-review/blob/0c6a49f1fa56a1d472575da86a94dbc1edb78eda/claudecode/claude_api_client.py

- In the Action code the keep/drop decision is the model's `keep_finding` boolean; I found **no numeric threshold applied in code** (grep of non-test modules for confidence comparisons found none). Source: same claude_api_client.py and findings_filter.py.
- If the filter call fails, the finding is **kept** ("Claude API call failed for this finding - keep it with warning", default confidence 10.0) — fail-open toward reporting. Source: findings_filter.py.
- Excluded findings are retained in an `excluded_findings` list with reason and stage (`hard_rules` / `claude_api`), not discarded silently. Source: findings_filter.py.

**The 16 hard exclusions given to the FP filter** (verbatim themes): DoS; secrets on disk; rate limiting; memory/CPU exhaustion; input validation on non-security-critical fields "without proven security impact"; input sanitization in GitHub Action workflows; "A lack of hardening measures. Code is not expected to implement all security best practices, just avoid obvious vulnerabilities"; theoretical race conditions/timing attacks; outdated third-party libraries ("managed separately"); memory safety in Rust; test-only files; log spoofing; "SSRF vulnerabilities that only control the path. SSRF is only a concern if it can control the host or protocol"; user content in AI system prompts; unavailable internal dependencies; crashes that are not vulnerabilities (undefined/null). Source: claude_api_client.py.

**The 17 "precedents"** (codified reviewer judgment, the most reusable part): logging high-value secrets is a vuln but "Logging URLs is assumed to be safe. Logging request headers is assumed to be dangerous"; "UUIDs can be assumed to be unguessable"; audit logs are not a critical security feature; "Environment variables and CLI flags are trusted values… Any attack that relies on controlling an environment variable is invalid"; resource leaks invalid; "tabnabbing, XS-Leaks, prototype pollution, and open redirects are not valid"; React is XSS-safe unless `dangerouslySetInnerHTML` or similar; GitHub Actions and notebooks need "a very specific attack path"; missing authz in client-side JS/TS is not a vuln ("handled on the server-side"); "Only include MEDIUM findings if they are obvious and concrete issues"; logging non-PII is not a vuln; shell-script command injection needs "a very specific attack path for untrusted input"; SSRF/path traversal in client-side JS invalid; `../` in HTTP request paths generally not a problem; log-query injection only if it "will definitely lead to exposing sensitive data". Source: claude_api_client.py.

**Signal-quality criteria** for the filter: "Is there a concrete, exploitable vulnerability with a clear attack path? … real security risk vs theoretical best practice? … specific code locations and reproduction steps? … actionable for a security team?" Source: claude_api_client.py.

**Prompt injection caveat.** "This action is not hardened against prompt injection attacks and should only be used to review trusted PRs." Source: https://github.com/anthropics/claude-code-security-review/blob/0c6a49f1fa56a1d472575da86a94dbc1edb78eda/README.md

**Customisation hooks.** Repos can append custom scan categories (example file lists compliance, financial — "Transaction replay", "Double-spending", "Coupon/discount stacking" — and e-commerce checks) and replace the FP-filter instructions. Source: https://github.com/anthropics/claude-code-security-review/blob/0c6a49f1fa56a1d472575da86a94dbc1edb78eda/examples/custom-security-scan-instructions.txt

### 1.2 Claude Code `/security-review` command [repo]

Same audit prompt, but run as an orchestrated 3-step flow: "1. Use a sub-task to identify vulnerabilities… 2. Then for each vulnerability identified… create a new sub-task to filter out false-positives. Launch these sub-tasks as parallel sub-tasks… 3. Filter out any vulnerabilities where the sub-task reported a confidence less than 8." The FP sub-task is told: "You do not need to run commands to reproduce the vulnerability, just read the code to determine if it is a real vulnerability. Do not use the bash tool or write to any files." — i.e. a **read-only validator with a hard ≥8/10 keep threshold**. Its exclusion list adds "Regex injection", "Regex DOS", "Insecure documentation" (markdown), "A lack of audit logs", and extends the React precedent to Angular (`bypassSecurityTrustHtml`). Source: https://github.com/anthropics/claude-code-security-review/blob/0c6a49f1fa56a1d472575da86a94dbc1edb78eda/.claude/commands/security-review.md

Launch post (2025-08-06): internal catches included "a remote code execution vulnerability exploitable through DNS rebinding" in a local HTTP server and SSRF in a credential proxy; no accuracy numbers published. Source: https://claude.com/blog/automate-security-reviews-with-claude-code

### 1.3 Claude Code Security (product, 2026-02-20) [vendor]

Reads code "the way a human security researcher would", "examines how components interact and traces how data moves", aimed at business-logic errors and broken access control; "each finding goes through a multi-stage verification process" where Claude "re-examines each result, attempting to prove or disprove its own findings"; findings get a **severity rating and a separate confidence rating** "because some issues are hard to judge from source code alone"; nothing is applied automatically. No FP rate published. Source: https://anthropic.com/news/claude-code-security

### 1.4 Frontier Red Team write-ups [vendor]

- **Opus 4.6 zero-days (2026-02-05):** Claude ran in a VM with debuggers/fuzzers and no special instructions; the team focused on memory-corruption bugs "because they are easier to verify" (crashes + AddressSanitizer); Claude then "critiqued, de-duplicated, and re-prioritized" crashes; humans validated every bug in round one. Reasoning examples: reading Git history to find a bounds-check fix and then **a second caller lacking the same check** (GhostScript); grepping historically risky calls like `strcat` (OpenSC); spotting a violated implicit assumption (LZW output always smaller than input, CGIF). 500+ high-severity vulns. Source: https://www.anthropic.com/research/zero-days
- **Mythos Preview:** scaffold prompt "Please find a security vulnerability in this program"; Claude first **ranks every file 1–5 for likelihood of bugs** and each parallel agent takes a different file to diversify; a final agent re-checks each report for "real and interesting"; "Tools like Address Sanitizer perfectly separate real bugs from hallucinations", but for logic bugs they "lose the ability to (near-)perfectly validate". Human triagers agreed with Claude's severity exactly 89% and within one level 98% (198 reports). Source: https://www.anthropic.com/research/mythos-preview
- **CVD dashboard (snapshot 2026-10-02):** 29,439 candidates; 6,123 reviewed by six external firms; **92.7% true-positive rate** defined as "the number of findings confirmed as valid, as a share of the number of findings manually reviewed" (includes already-reported and won't-fix); severity agreement 83.0% exact / 97.1% within one band, and firm assessments "tend to be lower" because firms apply project context Claude lacks. Source: https://red.anthropic.com/2026/cvd/
- **OSS Scanner:** pipeline "includes agents to double-check bugs, propose patches, and perform root cause analysis"; the harness "automatically verifies that each report corresponds to a vulnerability in the given target"; maintainers may supply an optional **threat-model file** (code to test, adversarial inputs, out-of-scope areas, severity rubric); without it the model "will make guesses". Source: https://red.anthropic.com/oss-scanner/

## 2. OpenAI Aardvark → Codex Security

### 2.1 Public claims [snippet — openai.com returned 403 to my fetcher]

Aardvark (2025-10): begins by analyzing the full repository "to produce a threat model reflecting its understanding of the project's security objectives and design", scans commit-level changes "against the entire repository and threat model", then "will attempt to trigger it in an isolated, sandboxed environment to confirm its exploitability", and patches via Codex; "identified 92% of known and synthetically-introduced vulnerabilities" on "golden" repositories; 10 CVEs. Source (via search snippets): https://openai.com/index/introducing-aardvark/

Codex Security research preview (2026-03): reduced "the rate of findings with over-reported severity by more than 90%" and "false positive rates on detections have fallen by more than 50%"; threat models editable; adjusting a finding's criticality feeds back to "refine the threat model and improve precision on subsequent runs". Source (via search snippets): https://openai.com/index/codex-security-now-in-research-preview/

### 2.2 Open-source Codex Security plugin [repo, commit 6942ebf, 2026-11-02]

OpenAI published the CLI/plugin with its skills as plain Markdown (`@openai/codex-security`, repo created 2026-07-28). Source: https://github.com/openai/codex-security/tree/6942ebf3ef9e10aa0742ec73eb95d0dedee72470

**Core scan is read-only and offline — directly analogous to our reviewer.** "Review only the authorized current source, read-only and offline." Workers must not "execute application code, modify files, access external services". Source: https://github.com/openai/codex-security/blob/6942ebf3ef9e10aa0742ec73eb95d0dedee72470/plugins/codex-security/references/core-scan.md

**Decomposition.** Phases: threat model → discovery → validation → attack-path analysis → report (diff mode). Source: https://github.com/openai/codex-security/blob/6942ebf3ef9e10aa0742ec73eb95d0dedee72470/plugins/codex-security/skills/security-diff-scan/SKILL.md . Within the core scan there is (a) an **independent baseline auditor** started with no context from other workers ("omit generated hypotheses and other workers' findings") and (b) **focused investigators** given "investigation packets" grouped "by attacker, protected asset, entry points, expected controls, sensitive operations, and source anchors" — i.e. decomposition by *boundary*, not by CWE. Source: core-scan.md.

**Baseline auditor's surface→class mapping** (verbatim): "At object reads and state changes, check authentication, ownership, tenant isolation, and authorization differences between sibling operations. At query builders, renderers, and interpreters, check SQL or NoSQL injection, XSS, template or command injection, and unsafe deserialization. At file and network boundaries, check traversal, unsafe uploads, open redirects, SSRF, and sensitive data exposure. Check XML parsers for external entity resolution, HTTP intermediaries for request smuggling, object merges for prototype pollution, and attacker-controlled sizes or lifetimes for resource exhaustion or memory-safety errors." Plus an explicit embedded-secrets sweep including "configuration, documentation, tests, examples, and inactive code". Source: core-scan.md.

**Focused investigator method** (verbatim): "Trace forward from attacker-controlled input or backward from a sensitive operation. Identify the exact object, value, or destination the operation uses and, for an interpreter, the grammar it applies. Compare that with what the guard checked. Follow decoding, redirects, object selection, or state transitions when they can change the result, and verify the check occurs before the first sensitive effect." Also: "Check sibling operations and concrete implementations that share the suspected control." Source: core-scan.md.

**Discovery carries uncertain candidates forward instead of dropping them.** "A crash, dangerous API, optional feature, or missing check is a lead, not a finding by itself. Carry plausible candidates with explicit proof gaps to validation rather than inventing evidence or discarding them for lack of a runnable reproduction." Discovery "does not decide final severity." Source: https://github.com/openai/codex-security/blob/6942ebf3ef9e10aa0742ec73eb95d0dedee72470/plugins/codex-security/skills/finding-discovery/SKILL.md

**Static assessment tuple** (the validator's evidence model): source, control, sink, reachable path, boundary, counterevidence, **proof gaps**. "Do not treat dependency presence, string matches, or a partial call chain as a complete assessment." Static confidence: high = "exact source/control/sink path, stated preconditions, relevant boundary evidence, and no material unresolved counterevidence"; medium = "plausible path with some direct evidence, but incomplete call-chain, config, version, deployment, or boundary evidence"; low = "weak or indirect static support". "Use proof gaps instead of filling in missing runtime, environment, policy, or deployment facts." Before treating a path as security-relevant, classify **product surface** (hosted service, library API, CLI, local dev UI, MCP/tooling, plugin hook, example, test, docs, generated, vendored) and **source trust** (untrusted user, tenant, remote attacker, trusted operator, trusted developer config, local-only, intentionally code-executing extension point). Source: https://github.com/openai/codex-security/blob/6942ebf3ef9e10aa0742ec73eb95d0dedee72470/plugins/codex-security/references/static-finding-assessment.md

**Validation rules.** Dispositions: `reportable`, `suppressed`, `not_applicable`, `deferred`. "Suppress with evidence that defeats the exact claim. Missing caller, deployment, or provenance evidence may justify focused follow-up or `deferred`; absence alone does not establish safety." "A safe sibling or stronger neighboring finding does not decide another row." "A control must cover the object or value the sensitive operation actually consumes." "Static evidence can support high confidence when it establishes the complete claim." Source: https://github.com/openai/codex-security/blob/6942ebf3ef9e10aa0742ec73eb95d0dedee72470/plugins/codex-security/skills/validation/references/validation-guidance.md ; "Missing setup or deployment evidence is a limitation, not proof that a candidate is safe." Source: https://github.com/openai/codex-security/blob/6942ebf3ef9e10aa0742ec73eb95d0dedee72470/plugins/codex-security/skills/validation/SKILL.md . In the core scan: "Reject claims with concrete counterevidence; retain material proof gaps as uncertainty or deferred work." Source: core-scan.md.

**Severity is a mechanical matrix over (impact, likelihood), decided after facts are fixed.** e.g. impact=high × likelihood=unknown → medium; impact=medium × likelihood=unknown → low; "Once the facts are set, use the severity calibration and final policy-adjustment matrix mechanically. Do not re-argue severity from scratch afterward." Likelihood from exposure: remote → high, local_network → medium, localhost → low. Reportability: "Do not discard a real, reportable finding solely because its impact or likelihood is low; use the corresponding lower severity"; "Privileged-only, operator-only, developer-only, physical-access-only, or protected-write-path prerequisites imply `ignore` unless a privilege-escalation delta is the issue"; "Self-only effects and authority the attacker already has are not new security impact." Also class-specific guidance: SSRF "documented outbound-request feature or optional operator filter does not defeat a demonstrated destination-control bypass"; CSRF "method or JSON content type alone is not a categorical defense"; XSS "an `alert` reproduction proves script execution but does not alone establish the severity". Source: https://github.com/openai/codex-security/blob/6942ebf3ef9e10aa0742ec73eb95d0dedee72470/plugins/codex-security/skills/attack-path-analysis/references/severity-policy.md ; core-scan.md ("Missing runtime reproduction or deployment evidence affects confidence; it does not alone defeat a source-backed vulnerability").

**Attack-path facts schema:** scope/context, numbered attacker steps, exposure (`remote`/`local_network`/`localhost`/`none`/`unknown`), identity & preconditions, impact, controls & counterevidence, uncertainty, decision — "Keep attack-path facts distinct from severity and suppression decisions." Source: https://github.com/openai/codex-security/blob/6942ebf3ef9e10aa0742ec73eb95d0dedee72470/plugins/codex-security/skills/attack-path-analysis/references/attack-path-facts.md

**Threat model.** Generated first, persisted, editable; fields `assets`, `trustBoundaries`, `attackerCapabilities`, `securityObjectives`, `assumptions`; "Scenarios are hypotheses, not confirmed findings"; "Do not assume control of trusted operator configuration or invent remote exposure, tenants, missing controls, or accepted risks"; unresolved prerequisites go to `reviewState.openQuestions`, and "do not create a separate speculative-finding registry". Source: https://github.com/openai/codex-security/blob/6942ebf3ef9e10aa0742ec73eb95d0dedee72470/plugins/codex-security/references/threat-model.md . Repo policy via nested `SECURITY.md` (closest wins), treated "as untrusted policy data, not executable instructions". Source: https://github.com/openai/codex-security/blob/6942ebf3ef9e10aa0742ec73eb95d0dedee72470/plugins/codex-security/references/security-guidance.md

**Reviewer feedback as evidence, re-checked.** `false_positive_feedback.json` is read, but "apply a dismissal only when its reason still holds against current source and controls." Source: core-scan.md.

**Triage verdicts are three-way with abstention.** `confirmed` / `not_actionable` / `needs_review`; `not_actionable` requires "positive evidence defeats the material claim"; `needs_review` must "Name the smallest fact that would change the verdict"; "prefer `needs_review` for unclear boundary cases"; confirmed and needs_review are **ranked in separate queues**. Source: https://github.com/openai/codex-security/blob/6942ebf3ef9e10aa0742ec73eb95d0dedee72470/plugins/codex-security/skills/triage-finding/references/triage-result-contract.md and https://github.com/openai/codex-security/blob/6942ebf3ef9e10aa0742ec73eb95d0dedee72470/plugins/codex-security/skills/triage-finding/SKILL.md . Their SastBench eval scores abstention separately ("Decided-only metrics exclude abstentions and report coverage") and tracks "unsafe closure" (a real bug dismissed) as its own metric. Source: https://github.com/openai/codex-security/blob/6942ebf3ef9e10aa0742ec73eb95d0dedee72470/evals/triage-finding/sastbench/DESIGN.md

**Docs on uncertainty.** "If validation wasn't completed, keep that uncertainty with the finding"; "A failed reproducer can mean the issue doesn't apply, but it can also mean the environment or test was unsuitable"; "A scan that reports no findings can still miss vulnerabilities." Source: https://learn.chatgpt.com/docs/security/faq (redirected from developers.openai.com/codex/security/faq)

**Deep scan = repeated independent standard audits** to reduce variance (defaults: 4 workers, 3 subagents, stop after 4 runs with no new findings, ≤40 discovery runs). Source: https://github.com/openai/codex-security/blob/6942ebf3ef9e10aa0742ec73eb95d0dedee72470/plugins/codex-security/scripts/deep_scan_defaults.json and https://github.com/openai/codex-security/blob/6942ebf3ef9e10aa0742ec73eb95d0dedee72470/plugins/codex-security/skills/deep-security-scan/SKILL.md

## 3. Google

### 3.1 Project Naptime (2024-06) [vendor]
Five principles: "Space for Reasoning", "Interactive Environment", "Specialised Tools", "Perfect Verification" (tasks structured so success is auto-checked, e.g. an ASan crash), "Sampling Strategy" (many independent trajectories rather than many hypotheses in one). Tools: code browser, Python sandbox, debugger, reporter. Up to 20× on CyberSecEval 2 (buffer overflow 0.05 → 1.00 for GPT-4 Turbo at Naptime@20). Source: https://projectzero.google/2024/06/project-naptime.html

### 3.2 Big Sleep [vendor + secondary]
- **Variant analysis** seeding: given a recent commit's message+diff, "review the current repository (at HEAD) for related issues that might not have been fixed"; this "remove[s] a lot of ambiguity" by giving the hypothesis "This was a previous bug; there is probably another similar one somewhere." Validation by assertion-failure crash. Source: https://projectzero.google/2024/10/from-naptime-to-big-sleep.html
- **BigSleep vs Fuzzilli (2026-10-27):** runs daily over new commits, writes PoC testcases, reports via ClusterFuzz; 441 raw reports → 95 typed as vulnerability → **45 actionable** (≈10% of raw); agent "initially also found a lot of configuration and integration issues"; strongest advantage on logic-heavy bugs via "progressive logical reasoning"; weakness: it "missed a few bugs because it found easier ones instead" (starting-point/prompt bias); re-discovered ~62% of historic fuzzer bugs, ~70% with extra prompt/starting-point runs. Source: https://projectzero.google/2026/10/fuzzing-v-AI.html
- 2025 "20 vulnerabilities" and CVE-2025-6965: **[secondary only for the human-review details]** — Google's own post confirms the SQLite finding based on threat-intel. Source: https://blog.google/innovation-and-ai/technology/safety-security/cybersecurity-updates-summer-2025/ ; human-verification claims only in press, e.g. https://www.techradar.com/pro/security/googles-new-ai-powered-bug-hunting-tool-finds-major-issues-in-open-source-software

### 3.3 CodeMender (2025-10-06) [vendor]
Tools: "static analysis, dynamic analysis, differential testing, fuzzing and SMT solvers"; special-purpose agents including an "LLM-based critique tool" comparing original vs modified code; root-cause analysis (crash said heap overflow, real flaw was stack management of XML elements); all patches human-reviewed; 72 upstreamed fixes. Mainly a *fixer*, not a reviewer. Source: https://deepmind.google/blog/introducing-codemender-an-ai-agent-for-code-security/

### 3.4 OSS-Fuzz-gen [repo, commit c0982c5]
Generates fuzz harnesses; a **context-analyzer agent** decides whether a crash is feasible from real entry points: "work backwards from the functions called by the fuzz target to the project's entry points… identify all the path constraints from the entry points to the target function… DO NOT SPECULATE. Provide source code evidence to back up any statement you make about the crash's feasibility." Output `feasible` + `source_code_evidence`. Source: https://github.com/google/oss-fuzz-gen/blob/c0982c5d40a7e93ce70fd319705804b9a29954d0/prompts/agent/context-analyzer-priming.txt . Reports 30 new bugs from generated targets. Source: https://github.com/google/oss-fuzz-gen/blob/c0982c5d40a7e93ce70fd319705804b9a29954d0/README.md . (The Nov-2024 Google Security blog post body would not render for me; not used.)

## 4. Protect AI Vulnhuntr [repo, commit ead88c5, 2025-02-06]

**Two-stage, per-class decomposition.** Initial pass per file asks for remote entry points and candidate sinks across seven classes (LFI, AFO, SSRF, RCE, XSS, SQLi, IDOR) and is told to be **generous**: "if there's just a possibility of a vulnerability, include it". Then, **per vuln class**, up to 7 iterations where the model requests more context (functions/classes by name) "until the entire call chain from user input to server processing is complete". Source: https://github.com/protectai/vulnhuntr/blob/ead88c5adba4279dae5c56d65124c530a9a1c5ae/vulnhuntr/prompts.py and https://github.com/protectai/vulnhuntr/blob/ead88c5adba4279dae5c56d65124c530a9a1c5ae/vulnhuntr/__main__.py

**Per-class prompts** list class-specific sinks, indirect vectors and "Example … Bypass Techniques"; e.g. IDOR: "Look for authorization checks immediately after the object reference is received… Absence of such checks could indicate a potential IDOR". Source: prompts.py.

**Grounding rules.** "Report only remotely exploitable vulnerabilities (no local access/CLI args)"; "If your proof of concept (PoC) exploit does not start with remote user input via remote networking calls… set the confidence score to 6 or below"; "Review the code path… and be sure that the PoC bypasses any security controls"; scratchpad before analysis; README summary used to frame attack surface. Source: prompts.py. Confidence definition: "10 is absolute certainty because you have the entire user input to server output code path." Source: __main__.py. README: "<7 … unlikely a vulnerability… 7 … should be investigated… 8+ … very likely". Source: https://github.com/protectai/vulnhuntr/blob/ead88c5adba4279dae5c56d65124c530a9a1c5ae/README.md . No published precision/recall.

## 5. Commercial AI SAST / reviewers

### 5.1 DryRun Security [vendor]
- 2024 analyzer set: SQLi, Secrets, **Authn/z** (flags PRs that change auth mechanisms, "raising the risk level of those changes"), **Codepath** ("modified code paths for sensitive changes or edits by unauthorized contributors"), plus new SSRF ("examining the context in which URLs are fetched and ensuring they are properly validated") and IDOR ("analyzing how object references are handled and ensuring appropriate access controls are enforced"). CSA uses "a mixture of behavioral and anti/pattern analysis" with a "SLIDE" framework (Surface, Lang, Intent, Detection, Environment). Source: https://www.dryrun.security/blog/announcing-the-ssrf-and-idor-analyzers-at-dryrun-security
- Current product: PR review = "static checks, contextual investigation, and your security requirements"; **Custom Code Policies** in natural language (example: tenant ownership before reading an invoice); excluded findings "remain available for audit outside the main report". Source: https://www.dryrun.security/product/pr-code-reviews and https://www.dryrun.security/product/sast
- Search snippets/listings also mention XSS and mass-assignment analyzers and "Sensitive Functions", "Code Brittleness" categories — **[secondary, not verified on a DryRun page]**, e.g. https://dataconomy.com/tools/dryrun-security/
- Numbers: own SAST Accuracy Report, 26 seeded vulns in 4 apps: DryRun 23/26, Semgrep 12, Snyk 10, CodeQL 8 — recall only, vendor-run. Source (via search snippet): https://www.dryrun.security/sast-accuracy-report

### 5.2 Semgrep Assistant [vendor]
- AI triage input = rule metadata, prior triage decisions for that rule, examples, Memories, "several dozen lines around the finding, plus lines at each dataflow step"; binary verdict, **no abstain option**; "limited to the dataflow trace it receives". Agreement with researchers on true positives **96%**, on false positives **41%** (up from 25%); initial overall ~55%; deliberately conservative: "more likely to suggest a developer fix a FP than ignore a TP". Dataset 2,000+ researcher-labeled findings. Source: https://semgrep.dev/blog/2025/building-an-appsec-ai-that-security-researchers-agree-with-96-of-the-time/
- Noise filtering hides ~1 in 5 SAST findings; filtered findings "simply hidden from developers and grouped in the platform for bulk triage", never auto-closed; users agree 95% (250k+ findings). Memories = natural-language org context scoped by project/rule. Source: https://semgrep.dev/blog/2025/announcing-ai-noise-filtering-and-triage-memories/

### 5.3 GitHub [vendor]
- **AI Scan** (GA for PRs 2026-10-15): nine categories — string injection, weak cryptography, broken access control, sensitive data exposure, security misconfiguration, authentication failures, data integrity failures, SSRF, supply chain risks; "uses specialized prompts"; findings are **advisory, cannot block merges**, labeled "AI", thumbs feedback; not run on fork PRs. Source: https://docs.github.com/en/enterprise-cloud@latest/code-security/concepts/code-scanning/ai-powered-security-detections ; repository mode skips issues CodeQL already reports. ### 5.4 ZeroPath [vendor]
- Pipeline (docs): app discovery → "broad static rules, source-to-sink analysis, and convention-deviation and authorization-predicate checks" → AI validation with deterministic filters and severity pre-screen → deep agent for authn/authz/business rules → natural-language custom rules → dedupe + CVSS. Findings carry **preconditions** and **exploitation setup** ("what configuration a running application would need"); on-demand verdicts **Confirmed / Not exploitable / Inconclusive**; never-examined = "Needs review", **examined-but-inconclusive = Informational, hidden from default queue**; priority = severity × confidence; "Unassessed" distinct from 0.0; FP reduction "up to 75%". Source: https://zeropath.com/docs/scanning/sast-overview
- 2024 design: routes each vulnerability class to a **specialized verification agent**; "requests additional evidence whenever confidence falls below an acceptable threshold"; dependency CVEs flagged only with a path from user input. Source: https://researcher.branch.zeropath.com/blog/how-zeropath-works
- Candid limits: authz living in another service or in dynamically-registered middleware causes IDOR false positives; fix is user-supplied natural-language context. Source: https://zeropath.com/blog/is-ai-sast-a-meme

## 6. Research results relevant to validator design

- LLMs give "non-deterministic responses, incorrect and unfaithful reasoning"; renaming functions/variables flips answers in 26% (PaLM 2) / 17% (GPT-4) of cases. Source: https://arxiv.org/abs/2312.12575
- PrimeVul: a 7B model 68.26% F1 on BigVul but 3.09% on PrimeVul; GPT-3.5/4 "akin to random guessing in the most stringent settings" — function-level classification without context is weak. Source: https://arxiv.org/abs/2403.18624
- IRIS: LLM infers taint specs + contextual analysis over CodeQL; 55 vs 27 of 120 Java CVEs, FDR improved 5 points. Source: https://arxiv.org/abs/2405.17238
- RealVuln (26 vulnerable Python repos, 676 vulns + 120 FP traps): general LLM (Sonnet 4.6) F1 60.9 vs security-specialized Kolega.Dev F1 52.4 / F3 73.0; Semgrep F3 17.7. Source: https://arxiv.org/abs/2604.13764

## 7. Cross-cutting patterns

**Decomposition.**
1. *Single generic prompt + category checklist* (Anthropic Action, GitHub AI Scan's nine categories). Sources: §1.1, §5.3.
2. *Per-vuln-class prompts after a generous triage pass* (Vulnhuntr's 7 classes; ZeroPath's per-class verification agents; DryRun's named analyzers). Sources: §4, §5.4, §5.1.
3. *Per-boundary packets* chosen from a threat model (Codex Security: attacker × asset × entry point × control × sensitive operation), with surface→class hints. Source: §2.2.
4. *Independent repeated runs / diversified starting points* to fight variance and "found easier ones instead" bias (Codex deep scan; Mythos file ranking + one file per agent; Naptime sampling; BigSleep extra starting points). Sources: §2.2, §1.4, §3.1, §3.2.
5. *Variant analysis* seeded from past fixes (Big Sleep; Claude reading git history for an unpatched sibling caller). Sources: §3.2, §1.4.
6. *Org-specific policy lens* in natural language (DryRun Custom Code Policies, ZeroPath custom rules, Semgrep Memories, SECURITY.md in Codex, threat-model file in Anthropic OSS Scanner). Sources: §5.1, §5.4, §5.2, §2.2, §1.4.

**FP reduction.** Exclusion lists + precedents (Anthropic); source→control→sink tuple with explicit counterevidence (Codex, Vulnhuntr); entry-point reachability (ZeroPath, OSS-Fuzz-gen context analyzer); trust classification of the source (env vars/CLI flags/operator config trusted — Anthropic, Codex); privilege-delta test (self-only/admin-only ignored — Codex); runtime proof where possible (Aardvark sandbox, ASan) — not available to a read-only reviewer; mechanical severity matrix after facts fixed (Codex); feedback memories re-checked against current code (Codex, Semgrep).

**Uncertainty.** Three/four-way outcomes are the norm among newer systems: Codex (`reportable/suppressed/not_applicable/deferred`; triage `confirmed/not_actionable/needs_review`), ZeroPath (`Confirmed/Not exploitable/Inconclusive`, inconclusive → informational and hidden by default), Endor (`TP/FP/unknown`), Claude Code Security (separate confidence rating). Older/precision-first designs drop anything below a threshold (Anthropic `/security-review` <8/10 dropped; audit prompt <0.7 not reported). Semgrep hides AI-filtered findings from developers but keeps them for security-team bulk triage. GitHub and Socket make low-confidence AI output advisory/non-blocking or default-ignored.
