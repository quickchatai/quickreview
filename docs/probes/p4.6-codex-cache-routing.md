# Codex cache routing, and what it decides for cache groups

## Question

Does codex route the prompt cache by `prompt_cache_key`, or by the session id the routing headers carry? The answer fixes how the SDK runtime shares a cache across a group of lens sessions, and with it whether lens rounds keep cache hits on most of a round's cost.

## Outcome

**No probe was run, and none is needed.** The question was already answered by the measurement in docs/prompt-caching.md: about 30 real calls on `gpt-6.1-sol`, each case a pair of separate pi processes over the same ~24k-token prefix. A small paid probe on a bare SDK session was planned, and replaced by this doc-only record: no model call of any kind was made for it, and no spend was incurred.
## Evidence

From docs/prompt-caching.md:
- pi uses its session id as the provider's cache key. `prompt_cache_key` and the routing headers (`session-id`, `x-client-request-id`) are all built from that one id.
- Two `--no-session` children, each with a random id, read 0 cached tokens even where their prompts were byte-identical.
- Two processes under one session id read 24,320 of 24,467 tokens when the second request came 2 s after the first.
- A second request that extends the first hits, whatever length it adds. A shared prefix that then diverges by about 250 words misses. That is why the cache groups need a warm-up that holds only the shared prefix.

What this shows: routing follows the session id. Every identifier the backend sees is derived from it, so a key edit alone cannot move a request to another cache. A `before_provider_request` payload edit that sets only `prompt_cache_key` leaves the session-id and `x-client-request-id` headers at the session's own id, and the measurements give no case in which that moves routing. Nothing measured supports routing by the key alone.

## Decision

**A shared session id per cache group, with group-scoped dispose**, decided from the existing measured evidence.

- The lens sessions of one cache group share one session id. Their key and routing headers then agree by construction, as they do for the pi children today (`--session-id <group key>`).
- No session of a group is disposed until the whole group is done. `dispose()` calls `cleanupSessionResources(sessionId)`, which closes every codex websocket held for that id. One lens finishing and disposing would cut a sibling's live websocket mid-request, so the group is disposed together.
- The warm-up takes no permit. It runs ahead of the group, holds only the shared prefix, and every lens request extends it.
- Rejected: unique ids per session with only `prompt_cache_key` rewritten to the group key. It is the shape the plan recommended, and the evidence says routing would not follow the key.

## For the SDK lens runtime

- A check that "the payload key equals the group key while ids stay unique" no longer applies. The check is that sessions of one group share the id, and that a sibling's dispose does not run before the group is done.
- The SDK lens runtime is bench-affecting and keeps its own gates. Whether the cache-hit share holds there is still measured, on faux and recorded fixtures first.
- Keep the VERIFY-ON-PIN tags on `before_provider_request`, `cleanupSessionResources` and `SessionManager.inMemory({id})`: the decision rests on pi's session-id-derived key and headers staying as measured.
